## Boundaries inspected and retained

- **Authentication:** `security.py` stores salted scrypt hashes, never recoverable account passwords. `main.py::issue_session` creates random opaque tokens, stores their SHA-256 hashes, sets HttpOnly/SameSite=Lax cookies, and requires Secure in production. Password changes/recovery revoke sessions. No master-password retrieval feature was added.
- **Authorization:** `services.py::job_for_user`, `owned_application`, document/source APIs, `outreach_api.py`, `operations_api.py` and `owner_console.py` check owner/role boundaries. Owner sensitive reads/actions require a fresh password, purpose, consent and audit; credential hashes/tokens/custom-answer vault are excluded. Ordinary users cannot select another tenant through a request owner_id.
- **Catalog privacy:** public facts are separate from encrypted profiles, saved records, application/document state and private imports. `catalog_query.py::visible_predicate` resolves only the request owner's direct/legacy memberships; aliases do not authorize another user's private record. Existing IDs/archives remain readable under their original authorization.
- **SQL:** user filters bind parameters through SQLAlchemy, escaped substring predicates and PostgreSQL query functions. Dynamic migration/index identifiers come from fixed metadata/operator code; benchmark schema names are generated and never public API input. No injectable raw-SQL API was identified in inspected routes. This is not a formal proof against every possible query bug.
- **External actions:** `automation.py::prepare_application` certifies submission only for the authorized local test portal. Real employers remain assisted/manual; unsupported JavaScript/CAPTCHA/MFA cases pause. Upload and submission require specific approval/checkpoints. `services.py`, `gmail.py`, `outreach.py`, `notification_delivery.py` distinguish prepared, uncertain, provider acceptance and confirmed application outcomes. No automatic retry of a persisted ambiguous outbound checkpoint.
- **OAuth:** `gmail.py` pins Google endpoints, uses PKCE, expiring single-use session-bound state, encrypted tokens and verified sender identity. Access-log callback codes/state are redacted by `security_logs.py`.
- **XSS:** React renders provider/user strings as text. The inspected `dangerouslySetInnerHTML` use is the static theme bootstrap in `app/layout.tsx`. Production CSP excludes unsafe-eval; inline script/style allowances remain a defense-in-depth limitation.
- **Secrets/files:** Fernet encryption protects candidate data, credentials, sessions and original/generated document content at rest. Documents download through owner checks with attachment headers. Parser proposals never silently update verified facts. Production configuration rejects missing persistent keys, insecure cookies/test mode, non-HTTPS origins, unprotected registration and unencrypted DB transport.
- **Logging:** worker failures generally persist exception class/static context, not request tokens/provider bodies. Validation omits original input. Operational scans have retention cleanup. Audit/messages/documents do not have complete retention/deletion/erasure workflows; do not advertise full privacy compliance.

## Rollout and recovery

No column/data/schema-version change; schema remains v7. Deploy code and dependency pins together. Pause outbound workers first, apply existing migration/backfill procedures if needed, then run `python -m app.catalog_migrations indexes` for the new partial unprojected-row index. It builds concurrently on PostgreSQL; legacy readers/writers remain compatible with the additive index. No data is deleted/rekeyed.

Canary on invitation-only read/discovery traffic. Keep a verified prior image and encrypted backup/key copy. If a query regresses, revert that query change; the extra index is harmless and can be removed concurrently after inspection. Do not roll dependency versions back to known vulnerable releases on an exposed parser. Prefer a forward fix or disable affected functionality. Restoring the whole database requires the Phase 4/5 writer-stop and outbound-reconciliation runbooks; never decrement migration history manually.

## Final executed gates and verdict

- Backend: **556 passed, 2 SQLite-variant skips, one existing deprecation warning**, 185.57s, exit 0; 28 PostgreSQL variants executed. Evidence: `artifacts/phase7-final-backend.xml` and `.json`.
- Frontend: lint/types/build/format, five cache/transport tests and OpenAPI drift check passed. Phase 7 browser rerun: 20 checks; 11 axe screen/theme evaluations, no serious/critical findings.
- Dependency scan after correction: zero known Python lock/npm advisories; pip check passed. Full before/after reports retained, including duplicate advisory IDs in the original feed.
- Real local encrypted pg_dump/restore, reference/byte preservation, paused-worker state and tampering cleanup verified. Backup timeout/output-error and parser interruption tests passed.
- Actual 10k/100k/1M PostgreSQL+HTTP results are in PERFORMANCE_REPORT. p95 at 1M/25 clients was 11.74s, not production acceptable. Correctness success is not performance certification.

**Verdict: locally regression-verified for controlled evaluation; not ready for unrestricted multi-tenant production or high-scale claims.** The remaining network/runner boundaries, load SLOs, quotas, durable event semantics and full-scale recovery/deployment gates are material, not paperwork. No hosting or real outbound integration certification was performed.
