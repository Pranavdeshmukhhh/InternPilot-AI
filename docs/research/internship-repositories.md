## `ibttf/internio`: implemented mechanisms and limits

The [README](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/README.md) describes a Django/PostgreSQL scraper, Next.js frontend, Celery/Redis scheduling and email subscriptions. The actual code implements the following narrower mechanisms:

- **Discovery:** [`back/Scraper/views.py`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/Scraper/views.py) handles a POST by fetching the GitHub HTML page for **Summer2024-Internships**, parsing table rows with BeautifulSoup, inheriting company names from continuation rows, recognizing closed/sponsorship symbols and extracting application URLs. It does not discover employer feeds or hackathon sources. Matching an existing `apply_link` prevents repeat creation and updates closed/sponsorship flags; this is an application-level lookup, without a demonstrated database uniqueness constraint.
- **Classification and filtering:** title substring rules assign categories; regex/string replacements normalize US-style locations. [`frontend/app/(default)/posts-list.tsx`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/frontend/app/%28default%29/posts-list.tsx) filters the fetched array by text, exact remote marker, location, sponsorship and categories. Multiple selected role/type checkboxes use conjunction, so selecting both internship and co-op requires both categories. These are metadata filters, without verified candidate eligibility or personalized matching. Sorting uses a special month mapping and current year, with 2023/2024 exceptions, which is unsuitable for general date ordering.
- **Intended scheduling has conflicting paths:** [`back/back/celery.py`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/back/celery.py) declares a 30-minute POST task, while [`back/back/settings.py`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/back/settings.py#L55) declares a two-hour scraper task. [`back/docker-compose.yml`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/docker-compose.yml) starts a Celery worker but no beat scheduler. [`frontend/vercel.json`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/frontend/vercel.json) declares daily cron, but [`frontend/app/api/cron/route.ts`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/frontend/app/api/cron/route.ts) exports only POST, unlike Vercel's GET cron invocation. [`back/back/tasks.py`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/back/tasks.py) also imports `.models`/`.serializers`, although those modules are under `Scraper`, not `back`. These static findings prevent treating the advertised schedule as verified working automation.
- **Actual email behavior:** [`back/Scraper/models.py`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/Scraper/models.py) registers a `post_save` hook that calls Django `send_mail` for every newly created job, passing **all subscriber addresses in one recipient list**. There is no per-user matching, approval, delivery deduplication, quiet-hours policy, durable delivery queue or uncertain-send recovery in this code. Email failure can interrupt scraping; the recipient-list design also creates a subscriber privacy concern.

Security and maintenance evidence:

- [`back/back/settings.py:75`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/back/settings.py#L75) sets DRF permissions to `AllowAny` and allows all CORS origins. Together with [`back/back/urls.py`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/back/urls.py) and `Scraper/views.py`, this exposes subscription-list reads, address-based deletes and scraper-triggering POSTs without application authentication. These patterns should not be reproduced in a shared app.
- The scraper's `requests.get/post` calls lack explicit timeouts/status validation and mostly lack network exception handling. Clearbit enrichment is another external dependency. A changed GitHub HTML layout, a hung upstream or a partial parse can break collection or silently produce an incomplete view.
- The complete tree contains a key-like path, **`back/my-key.pem`**. Its contents were deliberately not fetched or reproduced; its validity is unknown. Do not import the tree or treat embedded files as trusted credentials.
- [`back/requirements.txt`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/requirements.txt) pins Django 4.1.11, requests 2.31.0, Celery 5.3.4, Redis client 3.4.1 and gunicorn 20.1.0. [`frontend/package.json`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/frontend/package.json) declares Next `^13.4.1` and `latest` TypeScript/type dependencies. These are old or non-reproducible manifests; no claim of a clean dependency audit is made. The last source commit/push is June 2024, despite later repository metadata updates. [`back/Scraper/tests.py`](https://github.com/ibttf/internio/blob/5e3f97c4ab37300a7d73cedfb2698ea8c9b8dc46/back/Scraper/tests.py) is only a generated placeholder.

Useful independent ideas are normalized opportunity records, stable application-link identity, explicit closed state and filterable metadata. The exact code, historic season assumptions, subscription design and infrastructure should not be adopted.

## `SimplifyJobs/Summer2027-Internships`: actual data and update pipeline

The primary data is [`.github/scripts/listings.json`](https://github.com/SimplifyJobs/Summer2027-Internships/blob/801b67193266a23e8e0a94d40a26078aad07c5df/.github/scripts/listings.json), rather than just the rendered README. At the inspected revision it contains **17,287 records**, of which **4,851 have `active: true`** and **17,286 have `is_visible: true`**. These counts describe file flags across seasons, not verified open Summer 2027 roles. Example inspected records include inactive Summer 2026 roles, so a branch/repository title is insufficient as a season filter.

Actual fields include `id`, `source`, `category`, `company_name`, `company_url`, `title`, `url`, `locations`, `terms`, `degrees`, `sponsorship`, `active`, `is_visible`, `date_posted` and `date_updated`. The first inspected record has an explicit `terms: ["Summer 2026"]`, an employer ATS URL and `active: false`. Dates are Unix timestamps; they are not themselves job-availability checks.

## Implications for the internship and hackathon finder

Use official, permission-verified feeds or user-supplied authorized sources with bounded requests, timeouts, conditional fetches, provenance, stable identity and explicit stale/closed states. Keep source cadence distinct from end-user alert delivery. Persist candidate matching and deduplication independently of the presentation table.

Do not generalize any of these internship lists into a hackathon source: none implements a verified hackathon schedule, registration lifecycle or event eligibility model. Hackathon sources require their own permission/schema assessment, event date/timezone handling and registration-deadline semantics.

Independently implement saved metadata filters and candidate-specific scoring, leaving unknown graduation, country, sponsorship, compensation and deadlines visible for review. Source labels and title keywords alone must not become verified eligibility facts. For any future external notifications, use explicit per-delivery approval, private destinations, idempotent attempts, quiet hours and uncertain-outcome handling; the repositories above do not supply this foundation.
